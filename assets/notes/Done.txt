- feat(pairing): pair with the phone by QR or manual code, with the device token in Windows Credential Manager (spec `spec-n-zik-pc-bridge`, story 10, contract §4.2–§4.7, §5, §12)
  - Temporary HTTP listener (`PairingListener`, Ktor CIO on an ephemeral port) serving only `POST /nzik-pair/v1/offer`: `200 {accepted:true}` once per `requestId`, `410 PAIRING_REQUEST_EXPIRED` for an unknown, expired or used one, `400 BAD_REQUEST` for an invalid body, `404` for anything else; the `requestId` (128 bits, base64url) is renewed every 120 s on the same port and the listener closes after the `200` and whenever the pairing screen is left
  - QR (`QrCodeImage`, ZXing core) with the contract §4.3 payload: computer name (editable, 1–64 chars) and up to 4 LAN candidate IPs (`CandidateAddresses`: RFC 1918 only, virtual adapters excluded, default-gateway interface first); no candidate → straight to the manual form
  - After 60 s without a valid offer: explicit message (Windows Firewall / Public network) and switch to the manual form, the QR stays available
  - Manual pairing (contract §4.6): IP, port, code (normalised: upper case, spaces and dashes removed), device name; the port is prefilled with `42420` and the last phone IP of the session is prefilled after a revocation, a "Forget" or an "Edit IP" (memory only, never written once the pairing is erased) — user decision during the device test
  - `BridgeClient`: `GET /api/v1/meta` before `POST /api/v1/pairing/validate`; a `contractVersion` outside `1.x` shows "phone version incompatible" and stores nothing; `403 PAIRING_REJECTED` → "code invalid or expired", `429` → wait `retryAfterMs`; decisions from the error `code` only; the token is never logged
  - Storage (user decision): the `deviceToken` lives in Windows Credential Manager (generic credential "N-Zik Desktop Compagnon", hand-written JNA mapping to `CredWriteW`/`CredReadW`/`CredDeleteW`/`CredFree` in `WindowsCredentialSecretStore` since jna-platform 5.17.0 has no `WinCred`); the non-secret fields (`serverIps`, `serverPort`, `serverName`, `deviceId`, `deviceName`) live in `%APPDATA%\N-Zik Desktop Compagnon\pairing.json`; a missing token or a corrupt file reads as "not paired"
  - Start-up check (`PairingController`): phone unreachable → Retry / Edit IP (token and port kept, never a loss of pairing); a light Bearer probe (`GET /api/v1/library/songs?limit=1`): `401 DEVICE_REVOKED` confirmed by one retry 2 s later (`RevocationPolicy`, reusable by story 11) → token and `pairing.json` erased, re-pairing screen; `409 CONFLICT_ACTIVE_CLIENT` → "another PC (name) is connected", nothing erased, no automatic reconnection
  - N-Zik look copied and adapted from the phone: dark palette, Rubik type scale, rounded corners, `SectionCard` / `SettingsEntry` / `NZikButton`; Rubik fonts and 7 icons copied into `composeResources`; all UI text in `composeResources/values/strings.xml` (English)
